# 当前产品与验收

首版：GitHub仓库链接 → 岗位名称与JD → DeepWiki-Open全面Wiki与架构评审 → 对话讨论/纠正 → 确认个人贡献 → 简历Markdown。

建议针对模块、架构和能力方向，先说明业务问题、已有解法、必要性、替代方案与代价，再关联JD。允许没有改进建议，允许不引入Skill/MCP/multi-agent。最多3项，不强行凑数。项目缺少关键词不等于需要改造。

首版只需公开GitHub仓库链接，由DeepWiki-Open获取仓库、索引并生成全面Wiki。仅接受https://github.com/owner/repo，不执行源码。引用路径来自Wiki，跳转GitHub核对；可能复用DeepWiki缓存，不保证固定Git提交。全面分析目标不等于全覆盖。旧ZIP API保留兼容，界面不再要求上传。

讨论/尝试/已实现/已验证区分。简历以完整项目为主体，原项目目标、架构、技术设计与用户优化融合表达；没有讨论或改动也能根据已保存Wiki生成参考稿。用户确认的讨论设计可以进入参考稿，标明未实现；自行补充的数据保留来源和验证状态，不冒充系统实测。已验证状态仍需报告、来源、范围、限制。更正保留历史并让旧简历待复核。JD用于建议相关性与简历选材，不改变事实。旧搜索API保留兼容，搜索不在当前首版入口。

简历表达采用简洁STAR组织：项目目标/业务背景、技术架构与设计、优化行动及结果。原项目能力可直接作为项目描述，不自动宣称用户原创；设计想法不写成部署或已完成，预期指标不写成实测。默认页面选择模型按Skill提炼与写作，保留显式规则参考稿选项。

最新明确格式：项目简介（短段落）→技术亮点（通常2–4条，加粗主题，技术＋设计思路＋有来源结果）→项目成果（短段落）。不写端口、函数和参数等细节，不复制格式示例中的技术或指标。页面展示分层预览，Markdown导出保留审查未通过提示。

模型写作直接调用现有DeepSeek API：实际加载resume_composition Skill与writing-template.md，提供当前Wiki摘要、项目报告、JD和用户记录；岗位亮点评选→初稿→模型及规则检查→最多一次修订→复核。评选按HR/技术面试官视角，结合JD职责、工程深度、证据/状态、业务价值与可追问性选择1–4项独立主题，记录未选或证据不足的能力；没有材料的关键词不写成已有能力。不提供真实招聘结论或录用概率。正文主题及顺序与评选匹配，页面可展开评选依据。

DeepWiki只提供分析材料，不借用其问答系统提示或再次检索。检查未通过的正文保存为needs_review，模型异常不自动使用规则稿替代。产品全貌及生成最多八次请求（全貌一次、评选一次、两轮写作及独立HR/技术评审），首次Wiki分块另计最多64批，无子Agent或无限循环；审查仅辅助，不保证事实正确。评选结果、审查记录、Skill哈希和材料哈希保留。生成期间材料变化返回409，要求根据最新材料重做，不覆盖已保存草稿。

验收：链接校验与工作区隔离；真实服务缺配置明确失败，无模板兜底；引用路径绑定DeepWiki Wiki材料，不声称应用独立读取源码；必要性评审允许维持架构；链接到简历流程可运行；讨论不自动变完成；贡献更正传播；刷新保存记录。真实DeepWiki分析质量另需实际服务/模型与人工核对验证。

边界：本地单用户，无认证、自动编码、自动执行、私有Git克隆、PDF投递。简历首先保证真实性，文字风格进一步调整需用户反馈。

新增内容深度要求：亮点卡片记录具体问题、技术机制、有依据的取舍/结果、贡献归属与缺失问题。选题后检索完整Wiki相关段落补充，不增加模型请求数。HR/技术面试官内容反馈分为rewrite、needs_evidence、future_work；后两类不自动当成已实现成果。正文允许删减、重排或合并到已有主题。页面显示卡片和待补问题；当前卡片基于初选材料，补充证据用于正文与评审，不宣称卡片自动更新。
